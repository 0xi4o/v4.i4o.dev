**The win for today:** a written review of a design doc you did not write —
the [Tsundoku search doc](../exercises/tsundoku-search-design-doc) — with
each comment tagged by kind and severity and tied to a section, and a verdict
with the one thing that would change it. About forty minutes. Do not open
the exercise doc until section 4.

## What to do (read this first)

1. Read the [reviewer's form](../reference/reviewing-a-design-doc) — three
   passes, one comment shape, a verdict. Five minutes.
2. Do the sorting drill in section 2 so you know a useful comment from a
   remark before you write any.
3. Open the exercise doc, read its header, and review only what it asks
   for. Twenty minutes, three passes, comments in the shape.
4. Write the verdict. Run the checklist. Send me the review.

<KeyIdea>
	You already know everything a reviewer needs to check — it is the author-side rules from
	lessons 1–5, turned around. The skill in this lesson is restraint: comment on the decisions
	the header asked about, tie every comment to a goal or a section, end every comment with a
	question or a change, and leave taste at the door.
</KeyIdea>

## 1. What you are checking, and why (4 min)

Ubl's [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)
gives the reviewer's job in one line: bring experience to bear while change
is still cheap. Not to approve the prose, not to show what you would have
built — to find the thing the author could not see.

Sourcegraph's [status labels](https://github.com/sourcegraph/handbook/blob/main/content/company-info-and-process/communication/rfcs/index.md)
tell you what to read for: under "Reviewing problem" you check that the
problem definition is correct and ignore the design; under "Reviewing
solution" the goals are agreed and the design is open. Slatton's rule that a
doc should never surprise the reader is your detector — every place you
stop and think "wait, what about…" is a comment, and every place you think
"I'd have done it differently" is probably not.

Each author-side rule becomes a reviewer's question. Goals: outcome or
design choice? checkable? Non-goals: would anyone have expected it?
Context: any opinion in it? Design: choice, reason, cost, acceptance — all
four? Alternatives: real, and dismissed with a reason? Open questions: any
decisions hiding in there? Claims: a number behind every adjective?
Cross-cutting: present, and about the obvious concern? That list is the
three passes in the reference.

## 4. Do it (25 min)

Open the [Tsundoku search design doc](../exercises/tsundoku-search-design-doc).
It is a fictional project; the author is not you. Read the header first and
review what it asks for. Three passes, comments in the shape, five to ten
comments, verdict last. Write it in a Markdown file as if you were going to
paste it into the Discussion.

The doc has flaws of the kinds you have learned to avoid, and some things it
gets right. The answer key is in `NOTES.md` in this workspace, under
"Tsundoku key" — do not read it until you have sent me the review.

<Checklist
	title="Self-review: the review"
	items={[
		{ question: 'Did you review only what the header asked for?', why: 'A review that ignores "wanted" trains authors to stop writing headers.' },
		{ question: 'Does every comment carry a kind, a severity and a section?', why: 'Pre-sorted comments get acted on; unsorted ones get argued with.' },
		{ question: 'Does every comment end in a question or a proposed change?', why: 'An observation with no ask is a remark.' },
		{ question: 'Is every comment tied to a goal, a decision, or a missing section — never to your taste?', why: '"I’d have used X" bears on nothing.' },
		{ question: 'Did you note at least one thing to keep?', why: 'Not praise. A revision that loses the good paragraph is a worse doc.' },
		{ question: 'Is there a verdict, and for "request changes", the one item that would flip it?', why: 'The author should not have to infer the verdict from the tone.' },
		{ question: 'Five to ten comments?', why: 'Twenty comments means you reviewed the prose.' },
	]}
/>
